# 2026-10-10 iMessage 连发合并修复

## 生产核对与原因

- 发布前两个后端文件的 SHA-256 与本地 HEAD 一致，remoire / remoire-imessage 均 active；生产合并等待为 3 秒。
- 只查询了消息时间戳、角色、长度和队列状态，没有输出聊天正文或凭据。记录证明后续入站会落在上一轮生成期间；旧流程在等待期结束后固定批次，生成期间的补充只能成为下一轮。
- 代码还存在队列竞争：多个 flush 在取得生成锁前取走待处理内容，计时任务的取消/重排可能影响排队批次。旧测试关闭自动计时，仅证明手动 flush 可合并，未覆盖这条并发路径。
- 部分入站没有对应文字轮次，不能凭现有时间戳判定是否丢失；非文字/空内容现在明确忽略，不再延长等待或使回答作废。

## 本次修改

- 单消费者持有生成锁，以最后收到的有效文字的 monotonic 时间重新检查等待期；不再取消正在运行或排队的消费者。
- 生成期间收到补充：旧草稿返回 superseded，不保存 assistant、不发短信、不提取旧草稿记忆；原 user 消息保留。消费者等待最新补充安静下来后继续生成，聊天历史包含先前 user 和新补充。
- chat_service 的可选 reply_is_current 回调只用于 iMessage；模型返回后、工具开始前及回答保存前检查。网页调用无变化。已经执行的工具不撤销，也不通过取消任务重放。
- 合并等待仍为用户设置的 3 秒，没有改前端、模型槽位、关系档案、数据库结构或 Node 桥。
- 发布边界是 assistant 保存前检查；已进入保存/发送阶段的回复不撤回，之后来信进入下一轮。不是承诺直到手机实际收到前都能撤销。
- 生成不强行取消，作废草稿仍可能产生供应商费用；本次未添加真实模型调用。
